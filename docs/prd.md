# PRD: 화물 다단계 브로커리지 투명화 (AI 화물-차주 매칭 & 운임 적정성 체크)

> 이 문서는 `wireframe.html`(화주/기사 페이지 와이어프레임)과 `wireframe-notes.md`(와이어프레임 회의 요약) 기준으로 갱신됐다. 와이어프레임에 없는 기능은 [7. 추후 개선 항목](#7-추후-개선-항목)으로 분리했다.

## 1. 개요

화주가 카톡·전화·엑셀 등 비정형 채널로 전달하는 화물 요청을 AI가 자동 구조화하고, 조건에 가장 적합한 차주 1명을 즉시 추천해 전화로 바로 연결하며, 제시 운임이 시세 대비 비정상적으로 낮으면 경고한다.

- **왜**: 화물 운송의 32.1%가 3단계 이상 다단계 계약으로 이뤄지고, 그 결과 차주에게는 최초 운송료의 70% 미만만 지급된다(`research/b2b-logistics.md`). 카카오모빌리티가 오리엔테이션에서 직접 언급한 "정산·배차 디지털화 여지"와 정확히 맞닿아 있다.
- **1차 타겟**: 고정 계약 노선이 없는 **소규모·간헐적 화주**. (멘토 답변상 대형화주의 다단계 위계 구조는 이번 스코프에서 건드리지 않는다 — `mentor-qa-multi-tier-structure.md` 참고)
- **해커톤 스코프**: 당일 구현 가능한 데모 MVP. 실 데이터 연동 없이 mock 데이터 기반.

## 2. 사용자 스토리

- 화주로서, 나는 카톡/전화/엑셀로 받은 비정형 화물 요청을 텍스트로 붙여넣기만 하면 AI가 자동으로 구조화해주길 바란다. 왜냐하면 지금은 수작업 정리 후 주선사에 넘기는 과정에서 불필요한 중개 단계가 끼어들기 때문이다.
- 화주로서, 나는 구조화된 결과(출발지/도착지/화물종류/중량/희망운임/상차·하차일시)를 필드별로 직접 수정하고 싶다. 왜냐하면 AI 파싱이 완벽하지 않을 수 있고, 잘못된 정보로 매칭되면 신뢰가 깨지기 때문이다.
- 화주로서, 나는 내가 제시하려는 운임이 시세 대비 너무 낮은지 미리 경고 배너로 알고 싶다. 왜냐하면 비정상적으로 낮은 운임은 차주 착취로 이어지고 결국 매칭 실패로 돌아오기 때문이다.
- 화주로서, 나는 조건에 가장 적합한 차주 1명을 바로 추천받아 전화로 연결하고 싶다. 왜냐하면 여러 후보를 나열해 놓고 비교·협상하게 만드는 과정 자체가 다단계 중개가 끼어드는 지점이기 때문이다.
- 차주(기사)로서, 나는 내 활동 지역(출발/도착 시·도 및 시·군·구)을 설정해두면 그 조건에 맞는 화물만 추천받고 싶다. 왜냐하면 조건에 안 맞는 화물까지 일일이 확인하는 건 비효율적이기 때문이다.
- 차주(기사)로서, 나는 추천된 화물 카드에서 운임이 시세 대비 정당한지 배지로 바로 확인하고, 마음에 안 들면 목록에서 숨기고 마음에 들면 수락하고 싶다. 왜냐하면 지금은 다단계를 거치며 실수령액이 최초 운임의 70% 미만으로 깎이는 경우가 많기 때문이다.

## 3. 기술 결정 (ADR)

**데이터·랭킹 목표 구조 결정**: 백엔드는 Java(Spring Boot), 데이터베이스는 PostgreSQL + PostGIS를 사용한다. 화물 상·하차지와 기사 현재 위치·희망 도착지를 `geography(Point, 4326)`로 저장하고 거리 기반 후보 검색을 수행한다. 현재 in-memory/CSV 구현은 DB 연동이 늦어질 때 사용할 데모 폴백으로 유지한다.

| 구성 | 데이터 구조 | 역할 |
|---|---|---|
| 기본 경로 | PostgreSQL + PostGIS | 반경 필터, 거리 계산, 필수조건 검사, 기본 점수, 후보 50건 생성 |
| AI 경로 | OpenAI Responses API | 기사 자연어 선호를 반영해 후보 50건 재랭킹 |
| 데모 폴백 | CSV + in-memory 규칙 랭킹 | DB 또는 AI 장애에도 기존 추천 화면 유지 |

**AI 호출 결정**: OpenAI Responses API를 두 곳에 사용한다. `POST /parse`는 화물 원문을 Structured Outputs(JSON Schema strict)로 구조화하고, 기사 추천은 PostGIS가 압축한 후보 50건만 AI가 재랭킹한다. 정확한 거리·필수조건·최종 점수 결합은 서버가 담당하며 AI가 실패하면 PostGIS 기본 순위로 즉시 폴백한다. 파싱 계약은 [`llm-parsing.md`](./llm-parsing.md), 재랭킹 계약은 [`ai-route-ranking.md`](./ai-route-ranking.md)를 따른다. API 키는 서버 환경변수만 사용하며 프론트에 노출하지 않는다.

**매칭 로직 결정 (와이어프레임 회의 확정)**: 실시간 경매(입찰) 방식은 해커톤 시간·구현 배점(10%) 대비 리스크가 커서 배제. 대신 기사 mock 프로필에 `최소수락운임` 필드를 두고 다음 순서로 스코어링한다.
1. 화물종류 필터
2. 제시 운임이 최소수락운임 이상인지 확인
3. PostGIS로 현재 위치→상차지와 하차지→희망 도착지 거리를 계산해 기본 점수화
4. 상위 후보 50건만 기사 자연어 선호로 AI 재랭킹
5. 기본 점수 80%와 AI 점수 20%를 합치고, 동점이면 기본 점수·제시 운임·ID 순으로 정렬

기사 화면의 `GET /offers`는 동일한 순위 스냅샷을 페이지당 최대 20건 반환한다. 기본 폴백 규칙은 [`matching-ranking.md`](./matching-ranking.md), AI 재랭킹은 [`ai-route-ranking.md`](./ai-route-ranking.md), 공간 SQL은 [`postgres-distance-ranking.md`](./postgres-distance-ranking.md)를 따른다.

## 4. API 계약 초안

| 엔드포인트 | 기능 |
|---|---|
| `POST /parse` | 비정형 텍스트 → 구조화 JSON (출발지/도착지/화물종류/중량/희망운임/상차일시/하차일시, LLM 호출) |
| `POST /match` | 구조화 데이터 → **최적 매칭 차주 1명** (기사 현재 위치·활동 출발/도착지·최소수락운임 기반 점수 적용, 이름/차량/차량번호/운행지역/평점/완료율/최근운행/연락가능시간/최소수락운임/선호지역 반환) |
| `GET /fare-check` | 구간+화물종류 → 시세평균, 적정성 판정(정상/경고) |
| `GET /drivers/{id}/activity-region` | mock 기사의 현재 출발지·희망 도착지·반경·자연어 선호 조회 |
| `PUT /drivers/{id}/activity-region` | 출발/도착 지역과 선택적인 반경·자연어 선호를 설정. 서버가 좌표로 정규화해 저장 |
| `GET /offers?driverId={id}&page=0&size=20` | PostGIS 거리·운임 기본 점수와 AI 선호 점수를 결합한 추천 화물 페이지. `rankingMode(HYBRID/RULE_FALLBACK)`·거리·점수·추천 이유를 포함하고 첫 페이지 최상위 1건은 "AI 최적 매칭"으로 표시 |
| `POST /offers/{id}/accept` | 오퍼 수락 처리 |
| `POST /offers/{id}/hide` | 오퍼 숨기기 처리 (거절이 아닌 "숨기기"로 순화) |

> 화주 쪽은 매칭된 차주에게 **"전화하기" 버튼으로 외부 통화 연결**만 제공한다. 화주가 앱 내에서 특정 기사에게 요청을 보내고 기사가 승인/거절하는 시스템 내 상태 관리는 하지 않는다 (`POST /requests` 없음 — 7번 참고).

화면 상세, 엣지 케이스는 `feature-requirements.md`·`wireframe.html`·`wireframe-notes.md` 참고.

`POST /parse`의 원문·기준일·응답 필드·오류 처리는 [`llm-parsing.md`](./llm-parsing.md)를 따른다.

## 5. Out of Scope

- 실 로그인/인증 (드롭다운 또는 활동지역 설정으로 대체)
- 실제 결제·정산·선지급(팩토링) 처리 — 정산 유동성 문제는 이번 MVP 범위 밖, 피칭에서 로드맵으로만 언급
- 분쟁조정·보험 연계 기능 — 책임 소재 문제는 계약 로그 기록 수준까지만, 실제 조정 프로세스는 미구현
- 모바일 반응형 UI — 데스크톱 데모 전용
- 실시간 GPS/차량 위치 추적 — 위치는 기사 입력 또는 mock 좌표를 사용하며 PostGIS 거리 계산만 수행
- 실 화주/차주 데이터 연동 — 전부 mock/생성 데이터
- 실시간 경매(입찰) 기반 매칭 — 검토 후 명시적으로 배제. PostGIS 후보 검색과 AI 재랭킹으로 대체
- 다국어 지원
- LLM 프로덕션급 보안(레이트리밋, 어뷰징 방지, 키 로테이션)
- 수락 이후 배차·거래 상태의 프로덕션급 영속화. 데모의 수락·숨김은 메모리로 유지하거나 `driver_hidden_offer`만 선택적으로 사용한다.

## 6. 용어 정의

| 용어 | 정의 |
|---|---|
| 화주 | 화물 운송을 의뢰하는 주체 |
| 차주(기사) | 화물차를 소유·운행하며 운송을 수행하는 개인사업자 |
| 다단계 재하도급 | 화주 발주가 운송사→주선사→차주 등 3단계 이상을 거치는 구조 |
| 운임 적정성 | 동일 구간·화물종류의 시세 평균 대비 제시 운임의 비율 |
| 직접 매칭 | 중간 운송사/주선사 단계 없이 화주-차주가 바로 연결되는 것 |
| 최소수락운임 | 차주(기사)가 수락 가능한 최저 운임 기준값. 매칭 스코어링의 필터 조건으로 사용 |
| 활동 지역 | 차주(기사)가 등록한 출발/도착 희망 지역(시·도, 시·군·구 2단계) |

## 7. 추후 개선 항목

오늘 결과물(와이어프레임 기준)에는 포함되지 않았지만, 앞선 PRD 초안이나 팀 논의에서 나왔던 아이디어들. 우선순위가 정해진 것은 아니며, 시간이 남거나 본선 이후 고도화 시 검토한다.

- **화주 측 다중 후보 비교 UI**: 최적 매칭 1명 대신 여러 후보를 리스트로 보여주고 화주가 직접 선택하게 하는 기능. 오늘은 "협상·비교 과정 자체가 다단계를 재현한다"는 판단으로 단일 매칭 + 전화 연결로 단순화함.
- **화주-차주 인앱 요청/수락 플로우**: 화주가 앱 내에서 특정 차주에게 정식으로 요청을 보내고, 차주가 승인/거절해 상태가 관리되는 구조 (`POST /requests` 등). 오늘은 전화 연결로 대체하고 시스템 내 상태 관리는 하지 않음.
- **기사 "내 수입" 탭**: 완료 이력과 시세 대비 누적 수령률을 요약카드·그래프로 보여주는 화면. 차주 실수령 70% 미만 문제를 개인화된 숫자로 증명하는 효과가 있어 스트레치 목표였으나, 오늘 와이어프레임에서는 최종적으로 빠지고 그 자리를 추천 화물 리스트로 확장함.
- **정산 유동성(선지급) 연계**: 화주 대금 지급 지연(15~75일)과 차주 자금 유동성 문제를 해결하는 기능. `mentor-qa-multi-tier-structure.md`의 5번 이유(정산 지연 구조)에 대응하나 이번 MVP 범위 밖.
- **분쟁·책임 소재 대응**: 사고·분쟁 시 책임 소재 문제(멘토 Q&A 6번 이유)에 대한 실제 조정 프로세스.
- **매칭 알고리즘 고도화**: 수락·숨김 이력이 충분히 쌓인 뒤 학습 기반 랭킹으로 AI 점수 가중치를 개선한다. 실시간 경매는 계속 범위 밖이다.
