# PRD: 화물 다단계 브로커리지 투명화 (AI 화물-차주 매칭 & 운임 적정성 체크)

## 1. 개요

화주가 카톡·전화·엑셀 등 비정형 채널로 전달하는 화물 요청을 AI가 자동 구조화하고, 다단계 재하도급 없이 적합한 차주와 직접 매칭하며, 제시 운임이 시세 대비 비정상적으로 낮으면 경고한다.

- **왜**: 화물 운송의 32.1%가 3단계 이상 다단계 계약으로 이뤄지고, 그 결과 차주에게는 최초 운송료의 70% 미만만 지급된다(`research/b2b-logistics.md`). 카카오모빌리티가 오리엔테이션에서 직접 언급한 "정산·배차 디지털화 여지"와 정확히 맞닿아 있다.
- **1차 타겟**: 고정 계약 노선이 없는 **소규모·간헐적 화주**. (멘토 답변상 대형화주의 다단계 위계 구조는 이번 스코프에서 건드리지 않는다 — `mentor-qa-multi-tier-structure.md` 참고)
- **해커톤 스코프**: 당일 구현 가능한 데모 MVP. 실 데이터 연동 없이 mock 데이터 기반.

## 2. 사용자 스토리

- 화주로서, 나는 카톡/전화/엑셀로 받은 비정형 화물 요청을 빠르게 구조화하고 싶다. 왜냐하면 지금은 수작업 정리 후 주선사에 넘기는 과정에서 불필요한 중개 단계가 끼어들기 때문이다.
- 화주로서, 나는 적합한 차주와 바로 매칭되고 싶다. 왜냐하면 다단계를 거칠수록 중개 수수료가 누적되어 운임이 올라가기 때문이다.
- 화주로서, 나는 내가 제시하려는 운임이 시세 대비 너무 낮은지 미리 알고 싶다. 왜냐하면 비정상적으로 낮은 운임은 차주 착취로 이어지고 결국 배차 실패로 돌아오기 때문이다.
- 차주로서, 나는 매칭된 오퍼의 운임이 시세 대비 정당한지 한눈에 보고 수락/거절하고 싶다. 왜냐하면 지금은 다단계를 거치며 실수령액이 최초 운임의 70% 미만으로 깎이는 경우가 많기 때문이다.
- (스트레치) 차주로서, 나는 내가 받은 운임이 시세 대비 누적으로 얼마인지 확인하고 싶다. 왜냐하면 건별로는 착취를 체감하기 어렵기 때문이다.

## 3. 기술 결정 (ADR)

**Decision: 미정.** 백엔드는 Java(Spring Boot)로 확정됐으나, 데이터 저장·LLM 호출 방식은 팀 논의 후 확정한다. 아래 3개 후보안을 기록해둔다.

| 후보 | 데이터 구조 | 핵심 트레이드오프 |
|---|---|---|
| 안 A: In-memory Map | `ConcurrentHashMap` 등 static bean에 직접 저장 | 세팅 최속. 서버 재시작 시 데이터(시세표·기사 리스트) 전부 소실 |
| 안 B: Spring Data JPA + H2 | JPA Entity + H2(파일 모드) | `data.sql`로 mock 데이터 안정적 재현 가능, Controller-Service-Repository 표준 3계층 |
| 안 C: 비동기 파싱(WebClient+폴링) | 안 B와 동일 + 파싱 Job 상태 테이블 | LLM 호출이 요청 스레드를 막지 않아 UX는 좋으나, 하루짜리 데모엔 과투자 가능성 |

> Alternatives 거부 이유, Consequences는 안이 확정된 후 채운다.

## 4. API 계약 초안

| 엔드포인트 | 기능 |
|---|---|
| `POST /parse` | 비정형 텍스트 → 구조화 JSON (LLM 호출) |
| `POST /match` | 구조화 데이터 → 매칭 기사 리스트 (거리·차량조건 기준 정렬) |
| `GET /fare-check` | 구간+화물종류 → 시세평균, 적정성 판정(정상/경고) |
| `POST /requests` | 화주가 특정 기사에게 요청 전송 → 상태 생성(대기중) |
| `GET /offers?driverId={id}` | 특정 기사에게 매칭된 오퍼 목록 조회 |
| `POST /offers/{id}/accept` | 오퍼 수락 처리 |
| `POST /offers/{id}/reject` | 오퍼 거절 처리 |

화면 상세, 엣지 케이스는 `feature-requirements.md` 참고.

## 5. Out of Scope

- 실 로그인/인증 (드롭다운으로 기사 선택하는 것으로 대체)
- 실제 결제·정산·선지급(팩토링) 처리 — 정산 유동성 문제는 이번 MVP 범위 밖, 피칭에서 로드맵으로만 언급
- 분쟁조정·보험 연계 기능 — 책임 소재 문제는 계약 로그 기록 수준까지만, 실제 조정 프로세스는 미구현
- 모바일 반응형 UI — 데스크톱 데모 전용
- 실시간 GPS/차량 위치 추적 — 매칭 시 위치는 mock 데이터 기준 고정값
- 실 화주/차주 데이터 연동 — 전부 mock/생성 데이터
- 매칭 알고리즘 고도화 — 거리·차량조건 기반 단순 정렬 이상의 최적화(ML 기반 랭킹 등) 없음
- 다국어 지원
- LLM 프로덕션급 보안(레이트리밋, 어뷰징 방지, 키 로테이션)
- 오퍼 상태의 DB 영속화 — 세션 상태로 충분(서버 재시작 시 초기화되어도 무방, 단 안 B를 채택할 경우 H2로 자연히 유지됨)

## 6. 용어 정의

| 용어 | 정의 |
|---|---|
| 화주 | 화물 운송을 의뢰하는 주체 |
| 차주 | 화물차를 소유·운행하며 운송을 수행하는 개인사업자 |
| 다단계 재하도급 | 화주 발주가 운송사→주선사→차주 등 3단계 이상을 거치는 구조 |
| 운임 적정성 | 동일 구간·화물종류의 시세 평균 대비 제시 운임의 비율 |
| 직접 매칭 | 중간 운송사/주선사 단계 없이 화주-차주가 바로 연결되는 것 |
